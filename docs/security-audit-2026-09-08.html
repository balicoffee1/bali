Главное

Предыдущие итерации (M0–M7) закрыли платёжный флоу и state machine заказа — это видно по коду и держится хорошо. Но за пределами того скоупа осталось три класса проблем, и все три активны на проде.

Первое — секреты. Ротация от 06.09 закрыла .env, но в публичном репозитории остались ещё три источника: файл Island-Bali/Доступы с паролем root от прод-сервера, живая Telegram-сессия личного аккаунта и приватный ключ мерчанта РСБ. Все три лежат в git с самых первых коммитов.

Второе — авторизация. Флип DEFAULT_PERMISSION_CLASSES на IsAuthenticated закрыл анонимный доступ, но «аутентифицирован» в этом проекте означает «прошёл вход по SMS», то есть любой человек с телефоном. За этой границей открыто: выгрузка базы заказов с телефонами клиентов, прокси к CRM с операциями над бонусными балансами, редактирование меню — и повышение прав до суперюзера Django одним PUT-запросом.

Третье — транспорт. Приложение в сторах ходит на http://79.174.81.151/ без TLS, с принудительно снятыми защитами на обеих платформах. По этому каналу идут SMS-коды, JWT и номера банковских карт, которые бэкенд хранит в открытом виде.

A-01

Любой пользователь приложения делает себя суперюзером одним PUT

КритичноБэкенд

users/serializers.py:6-9 · users/views.py:381 · маршрут PUT /api/users/user_profile/

UsersSerializer объявлен через чёрный список: exclude = ("password", "last_login"). Значит DRF генерирует записываемые поля для всего остального, что есть в модели, — включая is_superuser, is_staff, role, groups и user_permissions. Тот же сериализатор используется на запись в user_profile.

Полная цепочка: вход по SMS → один PUT → доступ в /admin/ и в админ-панель со всеми правами, которые admin_api аккуратно раздаёт по ролям. Сигнал check_owner_exists ловит только role="owner"; admin и is_superuser проходят свободно.

curl -X PUT http://79.174.81.151/api/users/user_profile/ \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"is_superuser": true, "is_staff": true, "role": "admin"}'

Перевести сериализатор на белый список. Легитимный клиент шлёт ровно три поля (UserDto.toJson() в приложении), так что это не ломает контракт:

class UsersSerializer(serializers.ModelSerializer):
    class Meta:
        model = CustomUser
        fields = ("id", "login", "first_name", "last_name",
                  "email", "phone_number", "photo", "role",
                  "is_staff", "fcm_token")
        read_only_fields = ("id", "login", "phone_number",
                            "role", "is_staff")

После правки — проверить в БД, не поднял ли кто-нибудь себе права: SELECT id, login, role, is_staff, is_superuser FROM users WHERE is_superuser OR role != 'user';

M-01

Весь трафик приложения идёт без TLS

КритичноМобильное

lib/src/core/constant/keys.dart:18 · android/app/src/main/AndroidManifest.xml:9 · ios/Runner/Info.plist:35-39

База — http://79.174.81.151/, и обе платформенные защиты сняты явно и глобально: android:usesCleartextTraffic="true" без network_security_config, NSAllowsArbitraryLoads=true без исключений. WebSocket выводится из той же строки, то есть ws://, и Bearer-токен уходит в заголовке handshake открытым текстом.

По этому каналу передаются: коды подтверждения из SMS, access и refresh JWT, номера банковских карт (см. D-01), телефоны и состав заказов. Любой узел на пути — публичный Wi-Fi, оператор, транзит — читает и подменяет всё это. Приложение уже опубликовано в App Store и Google Play.

Домена нет, но провайдерское имя 79-174-81-151.cloudvps.regruhosting.ru резолвится на этот IP и годится под Let's Encrypt как временный вариант. Дальше: baseUrl на https://, usesCleartextTraffic убрать, NSAllowsArbitraryLoads убрать, на бэкенде включить SECURE_SSL_REDIRECT, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE и HSTS. Пока это не сделано, всё остальное в отчёте лечится лишь частично — перехваченный токен обходит любую серверную проверку.

D-01

Номера банковских карт хранятся в открытом виде

КритичноДанные

users/models.py:127-129 · users/serializers.py:12-21 · lib/src/feature/user_profile/data/bank_cards_repository.dart

Поле подписано «Зашифрованный номер карты», в модуле импортирован Fernet, рядом стоит модель EncryptionKey — но create_new_card кладёт PAN в базу как есть. Ничего из этого не используется: шифрование задумали и не дописали, а подпись поля осталась и вводит в заблуждение.

Замыкает круг сериализатор: get_card_number отдаёт сохранённое значение обратно клиенту целиком. Плюс __str__ печатает полный номер в списке объектов Django-админки. С учётом M-01 PAN ещё и летит по HTTP в обе стороны.

Хранить PAN нельзя — это прямое нарушение PCI DSS, и никакое шифрование в своей базе от этого требования не освобождает. Убрать эндпоинт bank_cards и экран в приложении; если нужен «сохранённый способ оплаты» — брать токен карты у LifePay, а у себя держать только последние 4 цифры и платёжный токен. Существующие строки в users_usercard — удалить, а не мигрировать.

A-02

quickresto — открытый прокси к CRM с операциями над бонусами

КритичноБэкенд

quickresto/views.py (12 классов) · quickresto/urls.py · маршруты /api/quick-resto/*

Ни один из двенадцати вьюсетов не объявляет permission_classes и не проверяет роль — то есть работает под дефолтным IsAuthenticated. Что доступно любому зарегистрированному пользователю приложения:

api/list/ и api/read/ — выгрузка клиентской базы CRM. api/create|update|remove/ — правка и удаление клиентов. bonuses/debit-hold/, credit-hold/, reverse/ — операции по бонусным счетам, то есть начисление себе средств.

Кофейня, чьими сохранёнными кредами (crm_email, crm_password) прокси аутентифицируется в QuickResto, выбирается по shop_city/shop_street из тела запроса — то есть тоже атакующим. Вызовы идут без таймаутов, CoffeeShop.objects.get() — без обработки DoesNotExist.

Самый быстрый безопасный шаг — снять path('api/quick-resto/', ...) из island_bali/urls.py: в мобильном клиенте нет ни одного обращения к этим маршрутам. Если функциональность нужна панели — вернуть под IsAdminRole из admin_api.permissions, кофейню брать из Staff текущего пользователя, добавить таймауты.

H-05

Сезонное меню и SEO-контент правит любой пользователь

ВысокийБэкенд

menu_coffee_product/views.py:145 · seo/views.py:8-21

SeasonMenuViewSet — полноценный ModelViewSet, у которого просто забыли permission_classes; дефолт IsAuthenticated открывает POST, PATCH и DELETE по сезонному меню, включая цены. У ColorModelViewSet и MarkdownModelViewSet стоит IsAuthenticatedOrReadOnly — тот же эффект для контента витрины.

Это ровно тот сценарий, ради которого меняли дефолт на IsAuthenticated: забытый permission_classes больше не открывает вьюху всему интернету, но всё ещё открывает её всем клиентам приложения.

H-06

Четырёхзначный код входа и включённый по умолчанию тестовый вход

H-08

Платёжные вьюхи ссылаются на поля, которых нет в модели

ВысокийБэкенд

acquiring/views.py:49, 84, 104, 133, 178 · acquiring/clients.py:83, 120, 141 · coffee_shop/models.py

Семь маршрутов вида /api/payment/{russian-standard,alpha,tinkoff,rsb}/… читают coffee_shop.bank_user, bank_password, bank_api_token, bank_shop_id. Ни одного из этих полей в модели CoffeeShop нет — есть только lifepay_* и crm_*. Каждый вызов падает AttributeError, то есть 500.

Удалить маршруты и модули Alpha/Tinkoff/RSB/RussianStandard. Реальный платёжный флоу — LifePay, он живой и покрыт тестами. Если какой-то из провайдеров планируется, писать его заново по образцу acquiring/providers.py, а не чинить это.

M-02

Токены в SharedPreferences, отозвать их нечем

ВысокийМобильное

lib/src/feature/auth/data/auth_repository.dart:54 · android/app/build.gradle:57 · settings.py — SIMPLE_JWT

Пара access + refresh пишется в SharedPreferences как обычный JSON — на Android это XML-файл в песочнице, на iOS plist. flutter_secure_storage в зависимостях нет, Keychain и Keystore не используются. На рутованном устройстве или из бэкапа значение достаётся напрямую.

Цена достаётся высокая из-за настроек на сервере: refresh живёт 30 дней, ROTATE_REFRESH_TOKENS=False, BLACKLIST_AFTER_ROTATION=False — то есть утёкший refresh действует месяц и его нечем отозвать, кроме смены SECRET_KEY (что разлогинит всех). В релизной сборке вдобавок minifyEnabled false и shrinkResources false, android:allowBackup не выключен.

Перенести сессию в flutter_secure_storage. Включить ROTATE_REFRESH_TOKENS и BLACKLIST_AFTER_ROTATION (token_blacklist в INSTALLED_APPS) — интерцептор в приложении уже умеет подхватывать новый refresh из ответа. Добавить android:allowBackup="false" и включить minify в release.
