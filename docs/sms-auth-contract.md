# Контракт SMS-аутентификации (для мобильного приложения)

Документ описывает новый порядок входа и регистрации по номеру телефона.
Серверная часть уже поддерживает и новый, и старый контракт одновременно —
переключение управляется настройками, так что приложение можно обновлять
без простоя.

## Что было не так

1. `registration_get_code` не отправлял SMS вообще и возвращал захардкоженный
   `code: "1234"`.
2. Код подтверждения возвращался клиенту в теле HTTP-ответа
   (`code`, `fcm_token`) — подтверждение номера не давало никакой защиты.
3. `POST /api/users/auth/` выдавал JWT по одному номеру телефона, без пароля
   и без кода. Любой мог войти под чужим номером.
4. Код нигде не хранился на сервере с ограничением по времени и попыткам.

## Новый порядок

### Шаг 1. Запрос кода

```
POST /api/users/registration_get_code/
{ "login": "+79991234567" }
```

Ответ `200`:

```json
{
  "text": "Код подтверждения отправлен по SMS",
  "is_registered": false,
  "expires_in": 300
}
```

- `is_registered` — есть ли уже такой пользователь; определяет, вести ли
  пользователя в регистрацию или во вход.
- `expires_in` — сколько секунд живёт код (`SMS_CODE_TTL`, по умолчанию 300).
- Поля `code` в ответе больше нет (в переходном режиме оно ещё приходит,
  приложение обязано его игнорировать).

Ошибки:

| Код | Когда | Тело |
| --- | --- | --- |
| `400` | `login` не похож на номер | `"login must be phone number"` |
| `429` | код уже запрашивали недавно | `{"error": "...", "retry_after": 42}` |
| `503` | SMS-шлюз недоступен | `{"error": "Сервер отправки СМС ..."}` |

При `429` показывайте таймер обратного отсчёта на `retry_after` секунд и
блокируйте кнопку «Отправить ещё раз».

### Шаг 2а. Регистрация нового пользователя

```
POST /api/users/get_or_create_user/
{ "login": "+79991234567", "first_name": "Иван", "last_name": "Иванов", "code": "8901" }
```

Ответ `201`: `{ "token": {"access": "...", "refresh": "..."}, "id": 11, "auth_type": "user", "is_staff": false }`

### Шаг 2б. Вход существующего пользователя

```
POST /api/users/auth/
{ "login": "+79991234567", "code": "8901", "fcm_token": "<push-токен устройства>" }
```

Ответ `200`: `{ "authorized": true, "token": {...}, "id": 11, ... }`

### Ошибки ввода кода (оба эндпоинта, `400`)

- `"Требуется код подтверждения из SMS."`
- `"Неверный код."`
- `"Код не запрашивался. Запросите новый код."`
- `"Код уже использован. Запросите новый код."`
- `"Срок действия кода истёк. Запросите новый код."`
- `"Превышено число попыток. Запросите новый код."`

Текст в поле `error` пригоден для показа пользователю как есть. После любой из
трёх последних ошибок нужно вернуть пользователя к шагу 1.

## Важно про `fcm_token`

Раньше поле `fcm_token` в ответе сервера содержало **код подтверждения**, а не
push-токен. Теперь:

- в ответах сервера это поле помечено устаревшим и в строгом режиме приходит
  `null` — не читайте его;
- в запросе `POST /api/users/auth/` `fcm_token` — это **настоящий push-токен
  устройства**, как и предполагалось;
- для регистрации push-устройства используйте `POST /api/users/fcm/register/`
  с `registration_id` и `type_device`.

## Правила на стороне сервера

- Код 4-значный, генерируется через `random.SystemRandom`.
- Хранится только SHA-256 хеш (соль — `SECRET_KEY`), в таблице
  `users_phone_verification`. Сам код в БД не попадает.
- Живёт `SMS_CODE_TTL` секунд (по умолчанию 300).
- Не более 5 попыток ввода, после — код сгорает.
- Одноразовый: успешная проверка гасит код.
- Новый запрос кода гасит все предыдущие коды этого номера.
- Повторный запрос кода не чаще раза в `SMS_RESEND_INTERVAL` секунд (60).

## Настройки (`.env`)

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SMS_LOGIN` / `SMS_PASSWORD` | — | Учётные данные iqsms.ru |
| `SMS_SENDER` | `BiBipTrip` | Имя отправителя, зарегистрированное у провайдера |
| `SMS_API_URL` | `https://api.iqsms.ru/messages/v2/send.json` | Эндпоинт шлюза |
| `SMS_TIMEOUT` | `10` | Таймаут запроса к шлюзу, сек |
| `SMS_ENABLED` | `True` | `False` — код только пишется в лог, SMS не уходит |
| `SMS_CODE_TTL` | `300` | Время жизни кода, сек |
| `SMS_RESEND_INTERVAL` | `60` | Антифлуд повторной отправки, сек |
| `SMS_EXPOSE_CODE` | `True` | Возвращать ли код в теле ответа (**временно**) |
| `SMS_ALLOW_LEGACY_AUTH` | `True` | Пускать ли без кода (**временно**) |

## Порядок выката

1. **Сделано.** Сервер обновлён, работает в режиме совместимости
   (`SMS_EXPOSE_CODE=True`, `SMS_ALLOW_LEGACY_AUTH=True`). Старое приложение
   продолжает работать, SMS при этом реально отправляются.
2. **Сделано.** Приложение (`happy_island`) переведено на новый контракт:
   `LoginBloc` разделён на события `Submited` (запрос кода) и `CodeSubmited`
   (подтверждение), проверка кода убрана из виджета и делается на сервере,
   код больше не выводится на экран. Остаётся собрать и выложить релиз.
3. **После того как доля старых версий станет приемлемой.** Выставить в `.env`
   (файл `Island-Bali/island_bali/.env` — именно его читает docker-compose):

   ```
   SMS_EXPOSE_CODE=False
   SMS_ALLOW_LEGACY_AUTH=False
   ```

   и перезапустить `web`. Отдельная миграция не требуется.

До шага 3 дыра в аутентификации остаётся открытой. Шаг 2 стоит не затягивать.

## Админ-панель (веб)

Веб-панель входит через `POST /api/admin/auth/login/` по логину и паролю с
проверкой роли — SMS-кодов не использует и этими изменениями не затронута.
Проверено: путь входа в панель полностью независим от `users.views.auth`.
