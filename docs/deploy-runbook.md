## 0. Что именно выкатывается и почему это связанный выкат

Ветка `user-cart`, два коммита:

- `2a8e2c7` — WS-only доставка состояния заказа и экрана смены
- `9f18833` — отправка отзыва и пустая корзина больше не отказывают

**Бэкенд и приложение обязаны выехать вместе.** Новый бэкенд удаляет два эндпоинта и три поля, которые вызывает и читает текущая установленная сборка:

| Что удалено | Что сделает старая сборка |
|---|---|
| `PATCH /api/orders/update-thank-you-dialog/{id}/` | 404 → диалог «Спасибо за заказ» открывается бесконечно |
| `PATCH /api/orders/update-order-cancelled/{id}/` | 404 → диалог «Заказ отменён» открывается бесконечно |
| поля `isThankYouDialogOpen` / `isOrderCancelled` / `isTimeChangedDialog` | отсутствуют в ответе → те же диалоги считают себя непоказанными |

То есть: выкатить только бэкенд — значит сломать диалоги у всех, кто не обновил приложение. Если обновить всех разом нельзя, вариант — выкатывать бэкенд без коммита, удаляющего эти поля и эндпоинты, и убрать их отдельно, когда старых сборок не останется.

**Ветка приложения (`bugfix/final` в `vektemok/Happy-Island`) на момент составления не запушена** — её нужно запушить и собрать.

## 2. Главный риск выкатки: миграции

В `Island-Bali/.gitignore` первой строкой стоит `**/migrations/*.py` — файлы миграций **не в git**. При этом entrypoint контейнера `web` на старте выполняет:

```
python manage.py makemigrations && python manage.py migrate && collectstatic && gunicorn
```

То есть сервер генерирует миграции сам, из моделей, поверх своей истории. Пока модели менялись мало, это работало. Сейчас изменений много, и локально это дерево уже разъезжалось — при подготовке пришлось руками приводить в порядок миграции `cart`, `orders`, `coffee_shop`, `menu_coffee_product`, иначе тестовая база просто не создавалась (`column cancellation_reason already exists`, `No constraint named unique_cart_product`).

Если то же случится на сервере, `migrate` упадёт → контейнер `web` уйдёт в crash-loop → **API ляжет целиком**.

Поэтому в пункте 5 миграции сначала проверяются в одноразовом контейнере и только потом применяются. Не запускайте `up -d --build` вслепую.

Отдельно: эту причину стоит устранить — убрать `makemigrations` из entrypoint и внести миграции в git. Но не в этот выкат.

## 5. Собрать образы и проверить миграции, не поднимая сервис

```bash
cd Island-Bali
docker compose build            # web, ws, celery, celery-beat — из одного Dockerfile
```

Проверка миграций в одноразовом контейнере, с отключённым entrypoint:

```bash
docker compose run --rm --no-deps --entrypoint "" web python manage.py makemigrations
docker compose run --rm --no-deps --entrypoint "" web python manage.py migrate --plan
```

Ожидается: добавление `event_seq`, создание `OrderDialogAck`, удаление трёх полей.

**Если `migrate --plan` или `makemigrations` падают — остановиться здесь.** Сервис ещё работает на старом коде, ничего не сломано. Прислать вывод, разберём.

## 6. Выкатить

```bash
docker compose up -d --build
docker compose ps              # web, ws, celery, celery-beat, nginx, redis, db — все Up
```

Три контейнера собираются из одного образа, и **все три должны быть пересобраны**: `web` публикует события, `ws` держит соединения, `celery` применяет платежи. Частичный выкат — это ровно та рассинхронизация, из-за которой в логах приложения были кадры без `event_seq`.

Логи первых минут:

```bash
docker compose logs -f --tail=100 web ws celery
```

Смотреть на: успешный `migrate`, отсутствие трейсбеков, в `ws` — `ws_connected` / `ws_snapshot_sent` при заходе приложения.

## 7. Проверка после выката

По логам приложения (`flutter run`), заказ от создания до завершения:

- [ ] `order_ws_connected`, следом `order_ws_snapshot_received audience=customer`
- [ ] при создании заказа — `order_ws_event_received ... event_seq=1`
- [ ] **нет строк `order_ws_event_without_seq`** — их наличие означает, что часть контейнеров осталась на старом коде
- [ ] смена статуса **в админке Django** доезжает до приложения (это была причина зависавшего диалога)
- [ ] диалог «Ожидание подтверждения» закрывается сам, когда бариста принял заказ
- [ ] отправка отзыва проходит и диалог закрывается (было: «Не удалось отправить оценку»)
- [ ] корзина после завершения заказа открывается пустой, а не с текстом DioException
- [ ] экран смены: колонки заполняются без HTTP-запросов, заказ переезжает между колонками по событию

Быстрая проверка отзыва прямо на сервере (Telegram по-прежнему может быть недоступен — теперь это не должно мешать):

```bash
docker compose logs --tail=200 web | grep -i "review_telegram_notification_failed\|review_email_notification_failed"
```

Эти строки в логе — нормально: рассылка не удалась, отзыв сохранён.
