**Принятые решения (зафиксированы до начала работ):**
1. **Fallback:** WS-only + одноразовый REST-снапшот, если сокет не поднялся за ~5 с. Никакого таймера.
2. **Ack диалогов:** отдельная таблица `OrderDialogAck`.
3. **Диалоги:** правило «кнопка → закрылся навсегда» применимо не ко всем — нужна типология по назначению (раздел 3). Кнопки с сетевым вызовом должны показывать прогресс.
4. **Скоуп:** customer + staff-экран + опрос оплаты LifePay. Проект не на проде — миграции и переработка схемы допустимы.

## 0. TL;DR

1. **Транспорт уже готов** (M2-M6): Channels/daphne/Redis, `/ws/orders/`, JWT в handshake, группы `orders.user.{id}` / `orders.shop.{id}`; на клиенте `OrderSocketService` с backoff, heartbeat и реакцией на connectivity/lifecycle. Задача — не «внедрить WebSocket», а сменить роль WS с *инвалидатора кэша* на *источник данных*.

2. **Сейчас WS не отменяет HTTP, а порождает его.** Событие несёт только `order_id` + `version` (`backend:orders/realtime.py:38-50`), клиент по нему делает `GET /api/orders/orders/`. Плюс `Timer.periodic(5s)` (`order_notification_scope.dart:88`) и ещё 4 внеплановых fetch.

3. **Главный блокер — серверные пробелы в публикации событий,** а не клиент. Создание заказа, изменение времени бариста (`staff/serializers.py:94`), `client_confirmed`, `is_appreciated` не публикуют событий вовсе. Снимем polling сейчас — диалог «Время изменено» перестанет появляться совсем (раздел 2.2).

4. **Ловушка `version`:** документирован как версия бизнес-состояния и не растёт на presentation-изменения, а клиент отбрасывает события правилом `version <= local`. Нужен отдельный `event_seq` (раздел 2.4).

5. **Маршрутизация по адресату** (уточнено при реализации — сначала я оценил это как утечку данных, это не так, см. 5.3): `publish_order_status_changed` слал один payload и в группу пользователя, и в группу кофейни. Утечки между пользователями тут нет — в обе группы уходит один и тот же заказ. Реальная проблема в другом: приложение у покупателя и у бариста одно и то же, staff-соединение подписано сразу на две группы, и без явного маркера `audience` customer-слой применил бы чужой заказ из shop-группы как «мой последний заказ». Маркер проставляет сервер (раздел 5.3).

6. **Диалоги — не один механизм, а три класса** по назначению (раздел 3). Правило «нажал → больше не открывается» корректно только для одного из них; для двух других диалог должен гаситься доменным состоянием, а не флагом. Сейчас все пять сделаны вперемешку, отсюда два бесконечных reopen'а.

7. **Прогресс на кнопке — блокирующая зависимость, а не косметика.** Все четыре диалога с кнопками закрываются только после успешной записи на сервер (ack или доменной мутации) — это и есть гарантия «второй раз не покажется». А `GradientButton` (`core/widget/gradient_button.dart`) не имеет loading-состояния вообще — только `isActive` и `onPressed`, двойной тап = два запроса; `DefaultDialog` всегда рисует крестик, который закрывает диалог мимо любой записи (раздел 3.4).

8. **Staff-экран:** `dispose()` отсутствует полностью — два таймера и три вручную созданных блока не освобождаются при уходе с экрана. Это надо чинить до перевода на подписки, иначе получим несколько живых подписчиков на одну группу (раздел 5).

9. **Оплата уже ходит по WS** — оба входа LifePay сводятся к `OrderStateService.payment_succeeded/failed`, которые публикуют события. Клиентский `_checkLifePayStatus` — это не чтение статуса, а «пинок» серверу проверить провайдера; правильное место для этого пинка — Celery внутри платёжного окна, механизм уже есть (раздел 6).

Оценка: backend ≈ 2-3 дня, mobile ≈ 2-3 дня, тесты ≈ 1-1.5 дня.

## 2. Часть A — отказ от HTTP-запроса статуса

### 2.1 Текущий контракт события и почему он требует REST

`OrderRealtimeSnapshot.to_payload()` (`backend:orders/realtime.py:38-50`):

```json
{"type":"order.status_changed","order_id":1234,"status_orders":"In Progress",
 "payment_status":"Paid","version":7,"updated_at":"...","cancellation_reason":"..."}
```

Мобильной `OrderView` для диалогов нужно ещё минимум: `updated_time`, `client_confirmed`, `is_appreciated`, `coffee_shop_name`, `time_is_finish`, `created_at`, `cart`, `full_price`. Их в событии нет — отсюда REST.

### 2.3 Целевой контракт

Два типа сообщений; оба несут **полный снапшот заказа в том же формате, что элемент списка REST** — чтобы переиспользовать `OrderView.fromJson` и не заводить второй парсер:

```jsonc
// сразу после accept() на сервере, до любых событий
{"type": "order.snapshot", "orders": [ /* 0 или 1 заказ */ ], "event_seq": 42}

// на каждое изменение
{"type": "order.status_changed", "order": { /* тот же формат */ }, "event_seq": 43}
```

- **Список, а не объект, в снапшоте.** Состояние блока — `MatchingState<List<OrderView>>`, весь UI читает `state.data!.last`. Список из 0-1 элемента (самый свежий по `id`) сохраняет тип состояния и снимает проблему недетерминированного порядка, из-за которой уже пришлось добавить `order_by('id')` (незакоммиченная правка `orders/views.py:164`).
- **Один тип события,** а не `order.cancelled`/`order.completed` — листенер и так один switch по комбинации полей (обоснование из M2, раздел 5.3).
- **Сериализация после commit, не под блокировкой.** Сейчас снапшот строится внутри `transaction.atomic()` (`services.py:36-40`). Полный заказ тянет `cart_data` (вложенный `CartSerializer`) — это лишние запросы под `select_for_update`. Перечитывать в `on_commit` (`select_related('cart','coffee_shop','city_choose')`) и сериализовать там: клиент получит состояние не старее события, а защита от гонок остаётся на `version`/`event_seq`.
- **Общий сериализатор с REST.** Иначе WS и REST разъедутся при первой же правке полей. Один базовый класс, два наследника (customer/staff, см. 5.3).

### 2.4 Ловушка: `version` и presentation-изменения

`Orders.version` документирован (`models.py:106-113`) как версия **бизнес-состояния**: «НЕ увеличивается на чисто presentation-изменения». Клиент отбрасывает события правилом `event.version <= local.version` (`order_view_bloc.dart:96-103`).

Начнём публиковать события на presentation-изменения (`updated_time`, ack) без инкремента `version` — клиент их молча выбросит. Решение: **`event_seq`** — отдельный монотонный счётчик событий на заказ, инкрементируется при каждой публикации (бизнес или presentation). `version` остаётся чистой бизнес-версией и оптимистичной блокировкой, клиент дедуплицирует по `event_seq`. Стоимость — одно поле + миграция.

Отдельно: **ack диалогов в собственном событии не нуждаются** — раз снапшот читается из БД в момент публикации, ack приедет в ближайшем следующем событии сам. Своё событие нужно только для синхронизации второго устройства.

### 2.7 Побочный эффект: пустое состояние

**Поправка к первой редакции** (вскрылось тестом при реализации). Я написал здесь, что `menu_screen.dart:93` даёт вечный спиннер пользователю без заказов, потому что `hasData` в `order_view_bloc.dart` требует непустого списка. Это неверно: одноимённый геттер есть у самого `MatchingState` (`data != null`, `matching_state.dart:73`), а **член класса всегда побеждает член расширения** — то есть версия из расширения была мёртвым кодом, который при чтении выглядел живым. Реально работал `data != null`, и пустой список спиннер снимал.

Мёртвый геттер удалён — именно он и ввёл в заблуждение. Развести «состояние получено» и «заказы есть» всё равно стоит, но по другой причине: `isReady` не сбрасывается на промежуточном `processing`, поэтому экран не мигает спиннером на каждом обновлении, а пустое состояние после снапшота считается полноценным.

### 2.8 Fallback (решение принято)

Одноразовый REST-снапшот, если сокет не дошёл до `connected` за ~5 с после старта/логина. Реализация: таймер запускается при переходе в `connecting`, отменяется при `connected`; при срабатывании — один `viewOrders()`. Повтор только на следующем цикле подключения. **Это не polling** — периодичности нет, и логировать этот путь отдельным тегом (`order_rest_fallback_used`), чтобы в проде было видно, как часто сокет не встаёт.

## 3. Часть B — типология диалогов и их жизненный цикл

### 3.1 Почему одного правила недостаточно

Правило «нажал кнопку → закрылось навсегда» корректно только для *информирующих* диалогов. У остальных другое назначение:

- диалог «бариста проверяет заказ» **не должен** гаситься навсегда — он обязан закрыться сам, когда бариста подтвердит; кнопки у него нет вовсе;
- диалог «время изменено» требует **выбора** (подтвердить/отменить), и гасит его результат мутации, а не факт закрытия; ack тут лишний и вреден — записав ack, мы скроем диалог у пользователя, который так и не ответил.

Отсюда три класса.

### 3.2 Классы диалогов

**Класс A — Ожидание (state-driven).**
Открывается и закрывается исключительно доменным состоянием. Кнопки подтверждения нет, ack нет и не должно быть. Задача — не дать пользователю уйти, пока идёт короткая операция на стороне персонала.
*Требования:* `barrierDismissible: false`, крестик скрыт, обязательно должен быть escape-hatch («Отменить заказ») — сейчас его нет, пользователь заперт до 15-минутного таймаута.
*Экземпляр:* «Ожидание подтверждения бариста».

**Класс B — Информирующий (ack-driven).**
Сообщает факт, домен от закрытия не меняется — поэтому нужен персистентный ack, иначе диалог возвращается на каждом следующем событии.
*Требования:* **прогресс на кнопке обязателен.** Кнопка запускает запись ack, показывает спиннер и закрывает диалог **только после успешного ответа**. Это даёт жёсткую гарантию «второй раз не покажется»: к моменту закрытия флаг уже лежит в БД, и никакая гонка со следующим событием его не обгонит. Оптимистичное закрытие (закрыть сразу, ack в фоне) такую гарантию даёт только в пределах сессии — при обрыве запись теряется и диалог возвращается после рестарта, поэтому от него отказались.
*Дизмисс жестом/свайпом запрещён* — иначе остаётся путь выхода без записи ack, то есть ровно та дыра, которую закрываем. Крестик, если он нужен по дизайну, ведёт себя как кнопка: тот же запрос, тот же прогресс.
*Экземпляры:* «Спасибо за заказ», «Заказ отменён».

**Класс C — Решение (decision-driven).**
Кнопка запускает мутацию домена, и именно домен гасит диалог. Ack не нужен.
*Требования:* **прогресс-индикатор на кнопке обязателен**; на время запроса обе кнопки disabled; закрытие **только по успеху** (сейчас закрытие стоит в `finally` — то есть и на ошибке тоже); при ошибке диалог остаётся открытым с сообщением и активными кнопками; дизмисс жестом запрещён (`barrierDismissible: false` + `PopScope(canPop: false)`). Крестик скрыт везде, кроме диалога оценки — там он и есть второй путь выхода и ведёт себя как кнопка с прогрессом (см. ниже).
*Экземпляры:* «Время изменено» (подтвердить/отменить), «Оцените заказ» (отправить).

**«Оцените заказ» — класс C с ack-путём выхода, без отдельной кнопки «Пропустить».**
Отдельная кнопка не нужна: **само закрытие диалога и есть отказ от оценки**. Два пути выхода, оба с прогрессом, оба закрывают диалог навсегда:
- «Отправить» → `POST /api/review/` → `is_appreciated = true` (гасит диалог доменно, как сейчас);
- закрытие (крестик или кнопка «Закрыть») → ack `feedback` → диалог больше не показывается, отзыв не создаётся.

*Почему ack, а не «пустой отзыв»:* записать Review без оценки нельзя технически (`evaluation` обязательно), а записать с дефолтной — значит накрутить рейтинг кофейни отказами пользователей: `_rating` инициализируется значением `5` (`order_notification_scope.dart:308`), то есть каждое закрытие «просто чтобы убрать окно» превратится в пятизвёздочный отзыв. Ack даёт ровно тот же UX («закрыл — больше не увидел»), не трогая витрину отзывов. Если пустой Review нужен именно как аналитика «показали, но не оценили», её лучше строить из `OrderDialogAck.acknowledged_at` — там уже есть и заказ, и время; альтернатива (сделать `Review.evaluation` nullable) дороже и меняет агрегаты рейтинга.

### 3.3 Целевая таблица

| Диалог | Класс | Условие открытия | Что закрывает | Ack | Прогресс на кнопке | Дизмисс |
|---|---|---|---|---|---|---|
| Ожидание подтверждения | A | `status == New && payment == Pending` и возраст < 15 мин | переход из `New` (accept → Waiting, либо Canceled) | нет | нет (кнопки нет) | запрещён; отдельная кнопка «Отменить заказ» = класс C |
| Спасибо за заказ | B | `status == In Progress` и нет ack `thank_you` | ack `thank_you` | ✅ | ✅ обязательно | запрещён |
| Заказ отменён | B | `status == Canceled` и нет ack `canceled` | ack `canceled` | ✅ | ✅ обязательно | запрещён |
| Время изменено | C | `updated_time != null && !client_confirmed && status ∉ {Canceled, Completed}` | `client_confirmed = true` **или** `status = Canceled` | нет | ✅ обе кнопки | запрещён |
| Оцените заказ | C | `status == Completed && !is_appreciated` и нет ack `feedback` | «Отправить» → `is_appreciated = true`; «Закрыть» → ack `feedback` | ✅ (путь закрытия) | ✅ обе кнопки | запрещён |

Добавление `!client_confirmed` в строку «Время изменено» чинит бесконечный reopen даже до внедрения всего остального — это самый дешёвый отдельный фикс, его стоит вынести вперёд.

### 3.4 Чего не хватает в UI-ките

Прогресс нужен теперь **во всех четырёх диалогах с кнопками**, а не только в «решающих», — то есть это блокирующая зависимость всей части B, а не косметика.

- **`GradientButton`** (`core/widget/gradient_button.dart`) — только `isActive` + `onPressed`, никакого loading. Нужен `isLoading` (спиннер вместо текста), блокировка повторного нажатия и `onPressed`, умеющий вернуть `Future` (либо внешний контроллер состояния кнопки). Сейчас двойной тап по «Подтвердить» = два запроса.
- **`DefaultDialog`** (`core/widget/default_dialog.dart:44-60`) — **всегда** рисует `CloseButtonWidget()` в шапке, и этот крестик закрывает диалог напрямую, мимо любой записи. Нужны два параметра: `showCloseButton` (скрыть для класса A) и `onClose`/`closeInProgress` — чтобы там, где крестик остаётся (диалог оценки), он вёл себя как кнопка с прогрессом, а не как немой дизмисс.
- **`CloseButtonWidget`** (`core/widget/close_button_widget.dart`) — голый материаловский `CloseButton()` **без `onPressed`**, то есть он всегда делает `Navigator.maybePop(context)` и никакого хука для записи ack в нём нет в принципе. Нужны `onPressed` и `isLoading` — иначе крестик физически невозможно провести через ack.
- **`_OrderFeedbackWidget.show`** (`order_notification_scope.dart:288-296`) — это `showModalBottomSheet` **без** `isDismissible: false` и `enableDrag: false`, то есть свайп вниз закрывает шторку мимо любой логики. Для диалога оценки оба флага обязательны, иначе путь «смахнул вниз» так и останется дырой, через которую диалог возвращается.
- **`OutlinedButton`** в «Время изменено» (`order_notification_scope.dart:832-865`) — тоже нуждается в disabled/loading; сейчас во время запроса «Отменить» можно нажать поверх уже идущего «Подтвердить».

### 3.5 Найденные баги (все — следствие смешения классов)

**B-1 (P0). «Время изменено» переоткрывается бесконечно.** Условие (`order_notification_scope.dart:188-190`) не проверяет ни `isTimeChangedDialog`, ни `clientConfirmed`. `_confirmOrder` ставит `client_confirmed=True`, но `updated_time` остаётся непустым → на следующем эмите состояния диалог открывается снова. Сегодня — каждые 5 секунд.

**B-2 (P0). Ack/мутация теряются в гонке — нет `await`.**
- `_confirmOrder` (:903-936): `RepositoryProvider.of<CartRepository>(context).confirmOrder(...)` вызывается **без `await`**, следом `context.pop()` в `finally` → `_onDialogClosed()` немедленно дёргает refetch, который может обогнать серверную запись.
- `_OrderCanceledWidget.cancelOrder` (:992-1001): `updateOrderCancelled(order.id)` тоже без `await`, `pop()` + `go(MenuScreen.routePath)` сразу.

**B-3 (P1). Двойной `pop` в `ThanksOrder`.** `PopScope.onPopInvokedWithResult(didPop: true)` (:592-596) вызывает `_updateOrderCancelled`, который сам делает `context.pop()` в `finally` (:690). При закрытии системным «назад» второй `pop` снимает нижележащий роут. Плюс имя метода не соответствует делу — внутри `updateThankYou`.

**B-4 (P1). «Оцените заказ» не подтверждается закрытием.** Гасится только фактом отправки отзыва (`reviews/views.py:66`). Свайп вниз → диалог возвращается. Дополнительно `_reviewOrder` (:487-507) делает `context.pop()` в `finally` даже при ошибке: пользователь видит «Ошибка при оценке», диалог всё равно закрывается, флаг не выставлен → вернётся.

**B-5 (P1). Семантическая мина в имени `isOrderCancelled`.** Поле называется «заказ отменён», а означает «диалог отмены уже показан». Это уже выстрелило: в незакоммиченной правке `orders/services.py` пришлось **убирать** установку поля из `cancel()` и `admin_override()` — сервис, честно выставляя «заказ отменён», гасил диалог до его показа.

**B-6 (P2). Закрытие диалога провоцирует его переоткрытие.** `_onDialogClosed` (:268-275) безусловно шлёт `fetch` → новое состояние → листенер снова прогоняет все условия. После части A этот fetch уходит, но петля остаётся через следующее WS-событие, если ack некорректен.

**B-7 (P3).** `setState` в `_onDialogClosed` может выполниться после `dispose` (колбэк `whenComplete` на :265) — нужен `if (!mounted) return;`.

**B-8 (P3).** Класс A заперт: `_OrderWaitingConfirmationWidget` — `barrierDismissible: false`, без кнопок, и если бариста не отвечает, пользователь ждёт 15 минут без возможности отменить заказ.

### 3.6 Механизм ack (решение принято)

```python
class OrderDialogAck(models.Model):
    order = models.ForeignKey(Orders, on_delete=models.CASCADE, related_name='dialog_acks')
    dialog_key = models.CharField(max_length=32)   # thank_you | canceled | feedback
    acknowledged_at = models.DateTimeField(auto_now_add=True)
    class Meta:
        unique_together = ('order', 'dialog_key')
```

- Один эндпоинт: `POST /api/orders/orders/{id}/dialog-ack/`, тело `{"dialog": "thank_you"}`, идемпотентный (`get_or_create`), скоуп по владельцу через `self.get_object()`, валидация `dialog_key` по белому списку.
- В снапшоте заказа — `"acknowledged_dialogs": ["thank_you"]`.
- На клиенте — один метод репозитория и одна проверка вместо четырёх разных полей. Новый диалог = новая строка-ключ, без миграции.
- **Таблица, а не `JSONField`:** два параллельных ack на JSON-колонке — read-modify-write гонка, теряющая запись; `unique_together` делает вставку атомарной. Плюс `acknowledged_at` бесплатно даёт аналитику «сколько людей закрывает диалог не читая».
- **Ack — мутация, идёт по REST.** Инвариант «WS read-only» (зафиксирован в `consumers.py:88-96`, любой неизвестный входящий тип → `{"type":"error","code":"unknown_type"}`) не нарушаем.
- Порядок в клиентском коде одинаков для классов B и C: нажатие → кнопка в прогресс → `await` запроса → закрытие **только по успеху**. При ошибке диалог остаётся открытым, кнопка снова активна, показывается сообщение.
- **Escape-hatch для офлайна.** Раз закрытие стало блокирующим, пользователь без сети запирается в «Спасибо за заказ». Поэтому после второй неуспешной попытки показываем «Закрыть всё равно»: диалог закрывается, ack кладётся в локальную очередь (`SharedPreferences`) и повторяется при следующем успешном соединении. Ack идемпотентен (`get_or_create`), поэтому повтор безопасен по построению.
- Локальный `Set<(orderId, dialogKey)>` в состоянии скоупа остаётся вторым контуром — он закрывает окно между успешным ack и приходом снапшота с обновлённым `acknowledged_dialogs`.

## 5. Staff-экран

### 5.1 Текущее состояние

- `staff_screen.dart:1198` — `Timer.periodic(30s)`, каждый тик 4 запроса: `LoadedOrder` + 3× `OrderByStatusLoadEvent`.
- `:894` — `_acceptanceTimer`, ещё один 30-секундный таймер, но это локальное напоминание «прими заказ» (`showNotification`), не сеть — его можно оставить как UI-таймер.
- **`dispose()` отсутствует полностью.** Оба таймера и три вручную созданных `OrderByStatusBloc` (`:1155`, `:1177`, `:1188`) не освобождаются при уходе с экрана. Это утечка независимо от WebSocket, и до перевода на подписки её надо закрыть: иначе получим несколько живых подписчиков на одну группу и дубли обновлений.

### 5.2 Что нужно

Серверная часть уже есть: consumer подписывает staff на `orders.shop.{place_of_work_id}` по `Staff.place_of_work_id` (`consumers.py:36-45, 57-60`). Нужны:
- `orders.shop_snapshot` на коннекте для staff — три колонки (Waiting / In Progress / Completed) одним сообщением;
- события в shop-группу с staff-payload'ом;
- на клиенте: `dispose()`, снятие `orderTimer`, подписка вместо таймера.

**Решение по применению событий (принято при реализации).** Изначально здесь предполагалось применять событие прямо в колонку (удалить из одной, вставить в другую). От этого отказался: состав колонок определяет сервер — `/api/staff/orders_by_status/` фильтрует не только по статусу, но и по 40-минутному окну (`sorting_time`), а `/api/staff/orders/` дополнительно отбрасывает всё, кроме `New`. Повторив эту логику на клиенте, мы завели бы второй источник правды о том, что видно в колонке, и рассинхрон был бы вопросом времени. Поэтому событие служит **триггером** перезагрузки колонок, а не данными: поллинг снят (запросы идут только когда что-то реально изменилось), но состав колонок по-прежнему считает сервер. Пачка событий схлопывается 300-миллисекундным дебаунсом в одну перезагрузку.

Это осознанный компромисс: staff-экран перестал опрашивать сервер вслепую, но остался на REST для содержимого. Полный переход на payload'ы имеет смысл делать вместе с переносом оконной логики в явный контракт, а не попутно.

### 5.3 Разный payload и маркер адресата

`publish_order_status_changed` клал **один и тот же `payload`** в обе группы:

```python
targets = [("customer", f"orders.user.{...}"), ("staff", f"orders.shop.{...}")]
for group_type, group_name in targets:
    channel_layer.group_send(group_name, {"type": ..., "payload": payload})
```

**Поправка к первой редакции этого раздела.** Я оценил это как утечку данных уровня P0 — при реализации выяснилось, что это неверно. В обе группы уходит один и тот же заказ: user-группа содержит ровно того покупателя, чей это заказ, а телефон клиента (`login` в `staff/serializers.py:15`) персонал этой кофейни и так видит в `/api/staff/orders/`. Межпользовательской утечки нет ни в одну сторону.

Настоящая проблема — маршрутизация на клиенте, и она серьёзнее для корректности, чем для приватности. Приложение у покупателя и у бариста **одно и то же**, а staff-пользователь держит **одно** соединение, подписанное сразу на свою user-группу и на shop-группу своей кофейни. Пока событие было «тонким» и лишь триггерило REST-перечитывание собственных заказов, это ничем не грозило. С полным снапшотом в payload'е customer-слой бариста применил бы **чужой заказ**, пришедший по shop-группе, как «мой последний заказ» — и показал бы бариста диалоги по заказу постороннего человека.

Решение: сервер проставляет в каждом кадре `"audience": "customer" | "staff"`, клиент по нему решает, в какой слой состояния класть событие. Плюс две формы payload'а по существу разные — покупателю нужен его заказ (`OrderRealtimeSerializer`), персоналу карточка для колонок с составом корзины и телефоном (`PendingOrdersAcceptSerializer`), — так что разделение всё равно требуется, просто по функциональной, а не по security-причине.

## 6. Оплата (LifePay)

**Статус оплаты уже ходит по WS.** Оба входа — webhook `lifepay_callback` (`acquiring/views.py:355-387`) и ручной `check_lifepay_status` (`:447`) — сводятся к `_apply_verified_lifepay_status` (`:314`) → `OrderStateService.payment_succeeded/failed` → публикация события. Причём статус из тела webhook'а не применяется напрямую: каждый входящий webhook только триггерит перепроверку через API LifePay (у провайдера нет подписи callback'а) — это правильно и менять не нужно.

**Что тогда делает `_checkLifePayStatus` на клиенте** (`order_notification_scope.dart:228-260`): это не чтение статуса, а *«пинок» серверу проверить провайдера* — на случай, когда webhook не пришёл. Правильное место для этого пинка — сервер, и механизм уже есть: `evaluate_payment_deadline` (T+90 с) и `finalize_payment_window` (T+120 с) в `services.py:434-503`, обе принимают `provider_status_checker`.

**Предложение:** добавить короткий опрос провайдера **внутри** платёжного окна — Celery-задача каждые 5-10 с от `payment_started_at` до `payment_deadline_at` (цепочка с `countdown` либо один task с ретраями, останавливающийся при достижении терминального payment-статуса). Тогда:
- клиент полностью освобождается от опроса, `_checkLifePayStatus` удаляется;
- оплата приходит по тому же каналу, что и всё остальное — событием `payment_succeeded`;
- редирект в корзину при pending-оплате остаётся, но управляется состоянием, а не результатом опроса.

Стоимость: ~10-20 обращений к API LifePay на заказ в худшем случае (только пока оплата реально в процессе). Если это дорого по лимитам провайдера — альтернатива компромиссная: оставить клиентский «пинок», но однократный, по кнопке «Я оплатил», без таймера.

## 10. Регресс, найденный на живом стенде (2026-09-03)

**Симптом:** статус заказа сменился на `Waiting`/`Pending`, а диалог «ждём подтверждения» не закрылся.

**Причина — не диалог, а мёртвое соединение, и это регресс от самого перехода на WS-only.**
В логе: `order_ws_disconnected close_code=4002` (сервер закрывает сокет, когда истекает access-токен, см. `orders/consumers.py`), после чего — тишина. Диалог не закрылся, потому что событие о принятии заказа до клиента просто не доехало.

Механика: access-токен живёт час (`SIMPLE_JWT.ACCESS_TOKEN_LIFETIME`), refresh — 30 дней, endpoint `/api/token/refresh/` на сервере есть, refresh-токен лежит в сессии приложения. **Приложение никогда им не пользовалось**: `TokenInterceptor.onError` на 401 просто разлогинивал. Раньше это маскировал поллинг — HTTP-запрос раз в 5 секунд ловил 401, и пользователя выкидывало на экран входа. Некрасиво, но заметно. После отказа от поллинга сетевых запросов не осталось вовсе: 401 ловить стало нечему, сервер закрывал сокет, клиент уходил в `authExpired` и ждал токена, который никто не выдаст. Приложение молча переставало получать обновления.

**Что сделано:**
- `AuthRepository.refreshAccessToken()` — обмен refresh-токена на новый access; успех публикуется в `authSessionSubj`, поэтому сокет переподключается сам. Параллельные вызовы схлопываются в один запрос; 400/401 от самого refresh (токен отозван/истёк) — разлогин, сетевая ошибка — нет.
- `OrderSocketService` при закрытии с 4001/4002 запрашивает продление. Ровно одна попытка на конкретный токен (иначе петля «подключились → 4002 → продлили → …»), но `ensureConnected()` (вернулась сеть, приложение из фона) снимает этот запрет — иначе истечение токена в момент отсутствия связи навсегда оставляло бы сокет мёртвым.
- `TokenInterceptor` на 401 сначала пробует продлить сессию и повторить запрос, и только потом разлогинивает.

**Второе, из того же лога:** пришёл кадр `order.status_changed` с `event_seq: 0`, и клиент отбросил его как устаревший (`0 <= 1`). Правило дедупликации исправлено: `event_seq == 0` означает «сервер не сообщил номер», а не «событие самое первое», и такой кадр применяется — сервер по определению знает состояние лучше клиента. Отбрасывание давало ровно то, от чего мы уходим: на сервере статус изменился, приложение об этом не узнало.

Откуда взялся кадр без номера — по логу установить не удалось: все пути публикации проходят через `_save_and_publish`, который инкрементирует счётчик до отправки, так что ноль оттуда прийти не может. Наиболее вероятно — частичный выкат (`web`, `ws`, `celery` собираются из одного образа, но это разные контейнеры). На клиент добавлен отдельный диагностический лог `order_ws_event_without_seq`, чтобы следующий прогон показал это явно.

Тесты после правок: **mobile 79** (было 72).

## 11. Вторая итерация разбора (2026-09-03, вечер)

Тот же симптом повторился уже без истёкшего токена, и в логе нашлась решающая деталь: кадр, который клиент считал устаревшим, **не сопровождался строкой `order_ws_event_received`** от транспорта. То есть он пришёл не из сокета вообще — это приложение применяло собственный ответ на `POST /api/orders/orders/` (`cart_screen.dart`, «применяем результат своей же команды немедленно»), а в ответе создания нет `event_seq`. После правки правила дедупликации такой кадр применяется, и всё это безвредно. К зависшему диалогу отношения не имеет.

**Настоящая причина — пропуск в инвентаризации точек мутации (раздел 2.2): Django-админка.**

`OrdersAdmin.save_model` сохраняла заказ обычным `obj.save()`. Это ещё одна точка изменения `status_orders`/`payment_status` в обход `OrderStateService`: `version` и `event_seq` не растут, событие не публикуется. Аудит покрыл HTTP-эндпоинты, Celery-задачи, сигналы и staff-сериализатор — но не `ModelAdmin`, и это моя ошибка. Пока приложение перечитывало заказы каждые 5 секунд, обход был незаметен: клиент всё равно рано или поздно видел новый статус. После отказа от поллинга это означает, что он не узнает об изменении **никогда**.

Симптом сходится дословно: «Статус заказа: Ожидание, Статус оплаты: ожидание оплаты» — это `verbose_name` из `Orders.StatusOrders` / `Orders.PaymentStatus`, то есть подписи в выпадающих списках именно админки Django.

**Исправлено:**
- `OrdersAdmin.save_model` проводит изменения `status_orders`/`payment_status` через `OrderStateService.admin_override` — он и предназначен ровно для ручного исправления: не проверяет допустимость перехода (блокировать админку state machine нельзя), но инкрементирует счётчики, публикует событие и пишет audit trail. Остальные поля формы сохраняются обычным путём. Создание заказа из админки публикует `order_created`.
- `staff/utils.update_order_comments` — `staff_comments` входит в payload клиента, теперь идёт через `update_presentation`.
- `CheckoutSerializer.create` (`POST /api/orders/checkout/`, вторая точка создания заказа мимо `perform_create`) публикует событие создания.

Тесты: **backend 124** (было 119) — в том числе сценарий из отчёта: смена обоих статусов разом через админку публикует ровно одно событие.

**Вывод на будущее.** Отказ от поллинга превратил каждый обход `OrderStateService` из «клиент узнает с задержкой до 5 секунд» в «клиент не узнает никогда». Инвентаризация точек мутации перестала быть аналитическим упражнением и стала инвариантом, который нужно защищать тестом. Раздел 2.2 стоит перечитывать как чек-лист при добавлении любого нового способа изменить заказ.

## 12. Экран смены целиком на WebSocket (2026-09-03)

Раздел 5.2 фиксировал компромисс: событие работает триггером перезагрузки колонок по HTTP. Компромисс снят — staff-экран переведён на WebSocket полностью.

### Что вскрылось по дороге

**Подписка из шага 6 не работала вообще.** Покупателю и персоналу приходят принципиально разные формы заказа: `OrderRealtimeSerializer` (с `user`, `city_choose`, `cart` числом) и `PendingOrdersAcceptSerializer` (с составом корзины и телефоном, но без `user`). Транспорт разбирал оба кадра покупательским `OrderView.fromJson`, который на staff-форме падает — кадр молча становился `UnknownRealtimeMessage`. То есть 30-секундный опрос я снял, а подписка взамен не срабатывала ни разу: экран обновлялся только при переподключении сокета. Регресс жил с шага 6 до этой правки.

### Контракт

| Кадр | Когда | Содержимое |
|---|---|---|
| `orders.shop_snapshot` | при подключении и по запросу экрана | заказы окна смены, три колонки, агрегаты, `shift_window_minutes` |
| `order.status_changed` (`audience: staff`) | на каждый переход | карточка заказа + `coffee_shop_id` + агрегаты |

Полное состояние — один раз, дальше дельты по одному заказу. Полное состояние на каждое событие не годится: колонка «Выполненные» ничем не ограничена по времени и растёт бесконечно, так что её пересылка дорожала бы вместе с ней.

- **`staff/queries.py`** — общий слой запросов. И REST-вьюхи, и realtime-снапшот собираются из одних функций, поэтому «что видно на экране» не зависит от транспорта; на это есть регресс-тест `ShopStateParityTests`.
- **`coffee_shop_id` в каждой дельте** — сотрудник может работать в нескольких точках, и тогда по одному соединению приходят дельты обеих.
- **`shop_snapshot_request`** — экран смены могли открыть посреди установленной сессии, когда автоматический снапшот давно ушёл. Это запрос на чтение: список кофеен сервер по-прежнему берёт из токена, инвариант «WS не мутирует состояние заказа» цел.
- **Агрегаты едут с каждой дельтой** — из колонок их не вывести (считаются по всей таблице), иначе цифры карточки смены застыли бы на моменте подключения.

### Клиент

Колонка (`OrderByStatusBloc`) знает свой статус и сама решает судьбу дельты: заказ своего статуса — upsert, чужого — удаление. Дельта до снапшота игнорируется: из одного заказа состав колонки не восстановить. Порядок повторяет серверный (`-created_at` в колонках, `time_is_finish` в списке непринятых).

Из staff-экрана убраны все четыре HTTP-запроса: стартовая загрузка, перезагрузка по событию, загрузка при переключении вкладки и pull-to-refresh (теперь просит свежий снапшот тем же каналом). `LoadedOrder`/`OrderByStatusLoadEvent` остались в блоках как аварийный путь, но ни один виджет их больше не диспатчит.

Тесты: **backend 134** (было 128 до этого раздела), **mobile 91** (было 79).

### Что осталось как было

Сознательно не тронуто, чтобы переезд на другой транспорт не менял то, что видит человек на смене:

- колонки Waiting / In Progress / Completed не ограничены по времени — «Выполненные» растут бесконечно, и снапшот при подключении растёт вместе с ними;
- агрегаты считаются по всей таблице заказов, без фильтра по кофейне: бариста видит цифры по всей сети.

Оба места помечены в `staff/queries.py`. Чинить их стоит отдельно и осознанно — это изменение того, что показывает экран, а не транспорта.
