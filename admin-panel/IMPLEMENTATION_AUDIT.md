# Аудит реализации Admin Panel

Дата проверки: 24 августа 2026.

## Результат

Проект перешёл из состояния статического прототипа в запускаемую связку frontend + Admin API foundation. Frontend собирается, вход и восстановление JWT-сессии реализованы, mock-режим отделён от рабочего API, роли согласованы с backend, а модель журнала действий снабжена миграцией.

## Что уже реализовано

| Блок | Состояние | Комментарий |
|---|---|---|
| Design System и Layout | Работает | Sidebar, Header, UI Kit, токены Happy Island; проверено на 1280 и 1024 px |
| Авторизация | Работает | Login UI, access/refresh JWT, восстановление и сброс сессии, rate limit входа |
| RBAC | Основа готова | `owner`, `admin`, `moderator`, `support`; read/write permissions разделены на Admin API |
| Dashboard | Частично | KPI, график, топ товаров и live-заказы отображаются; часть аналитики пока приблизительная |
| Пользователи | Частично | Список, поиск, блокировка, назначение роли; нет сброса сессий и полной истории |
| Меню | Частично | Категории, товары, цены S/M/L, стоп-лист; нет полноценного CRUD добавок/вкусов и загрузки фото |
| Заказы | Частично | Таблица, Kanban, детали, смена статуса и причина отмены; нет WebSocket/long-polling и возвратов |
| Смены | Read-only | Список сотрудников и смен; нет операционного управления сменой |
| Отзывы | Read-only | Список и фильтры; нет ответа клиенту, модерационного статуса и CSV-экспорта |

## Критические дефекты, исправленные в этой итерации

1. Отсутствовал `src/main.tsx`, поэтому Vite не мог собрать приложение.
2. Панель автоматически открывалась с правами Owner без авторизации.
3. Backend принимал вход без пароля и раскрывал существование логина разными ответами.
4. Любая ошибка API незаметно переключала frontend на mock-данные, что могло имитировать успешную запись без изменения PostgreSQL.
5. Access JWT фактически не сохранялся после реального входа и не обновлялся refresh-токеном.
6. `moderator` и `support` использовались в коде, но отсутствовали в `CustomUser.ROLE_CHOICES`.
7. Проверка `is_staff` давала сотрудникам более широкие Admin API права, чем определено матрицей RBAC.
8. Для `AdminActivityLog` не существовало миграции.
9. UI менял статус заявки на франшизу, но соответствующего поля в Django-модели не было.
10. CORS был объявлен как allow-all без подключённого middleware; теперь используются явные origins.
11. SMS и OneSignal credentials были записаны в settings; код переведён на env-переменные. Скомпрометированные значения следует ротировать, поскольку удаление из текущего файла не очищает историю Git.

## Оставшиеся риски

- Django-проверка и API-тесты не запущены: локальный `venv` существует, но Django в нём не установлен.
- Автоматизированных frontend/backend/E2E тестов пока нет.
- Acquiring/CRM passwords хранятся в модели в открытом виде; нужен encrypted-at-rest слой и маскирование API.
- Dashboard выбирает первые доступные товары вместо агрегации фактических продаж; метрика новых пользователей также требует поля даты регистрации.
- Push-рассылка выполняется синхронно и подавляет исключения; её следует вынести в Celery с журналом результатов.
- Нет optimistic concurrency/versioning: два администратора могут перезаписать изменения друг друга.
- Bundle frontend около 690 KB до gzip; для production нужны lazy routes/chunk splitting.
